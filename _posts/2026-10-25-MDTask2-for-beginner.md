# 栈的基本知识

程序运行起来以后，代码、全局变量、堆和栈等内容都会被放进进程的地址空间。栈是其中的一块内存区域，由程序自动管理，专门用来保存函数调用时需要临时记住的东西，比如局部变量、调用者的状态和函数结束以后应该返回的位置。

栈的数据结构就是后进先出（LIFO）。计算机里的栈通常从高地址往低地址长，这个方向可以记一下，因为堆和它是相反的。

32位程序里，栈指针叫`esp`，帧指针叫`ebp`；64位程序里分别叫`rsp`和`rbp`。`rsp`或者`esp`始终指向当前栈顶，程序每往栈里放一次数据，它就向低地址移动；取走数据时再向高地址移动。32位程序一次通常移动4字节，64位程序一次通常移动8字节。

如果要把一个寄存器里的值放进栈中，可以使用`push`；要从栈顶取出来，可以使用`pop`。以64位为例，这两条指令做的事情可以近似写成：

```asm
push rax    ; rsp = rsp - 8; [rsp] = rax
pop rax     ; rax = [rsp]; rsp = rsp + 8
```

只记住栈指针会增加和减少还不够，真正和pwn有关的是函数调用时栈上会出现什么。先看一段最简单的C代码：

```c
#include <stdio.h>

int add(int a, int b) {
    int sum = a + b;
    return sum;
}

int main(void) {
    int x = 1;
    int y = 2;
    int result = add(x, y);
    printf("%d\n", result);
    return 0;
}
```

从源代码看，就是`main`把1和2传给`add`，再接收计算结果。但CPU不会理解“把参数传给函数”这种抽象说法，它必须知道参数具体放在哪个寄存器或者哪一段栈上，也必须知道`add`执行结束后应该回到哪里继续执行。编译器会按照一套叫作“调用约定”的规则来安排这些内容。

这里先看32位Linux最常见的cdecl调用约定。为了把过程讲清楚，我们先不考虑编译器的优化，否则编译器很可能直接把1和2相加得到3，把整个`add`调用优化掉。

调用开始时，`main`先把参数从右往左压栈，所以先放入`2`，再放入`1`。接着执行`call add`，这个`call`并不会直接跳过去就结束了，它会先把`call`后面下一条指令的地址压到栈上，再跳到`add`的入口。这个被压进去的地址就是返回地址，函数结束后能不能回到正确的位置，全靠它。

进入`add`后，编译器通常还会生成一段“函数序言”：先保存`main`原来的`ebp`，让函数结束时能够恢复调用者的栈帧；再把当前的`esp`赋给`ebp`，把这里作为`add`自己的栈帧基准；最后把`esp`继续往低地址移动，给`sum`这样的局部变量留空间。函数执行到尾声时，再用`leave`和`ret`按相反的顺序恢复现场。

对应的关键指令可以简化为：

```asm
; main中调用add
push 2
push 1
call add

; add的函数序言
push ebp
mov ebp, esp
sub esp, 0x10

; add的函数尾声
leave
ret
```

`leave`可以近似理解成下面两条指令的组合：

```asm
mov esp, ebp
pop ebp
```

它先把`esp`恢复到当前函数的栈帧底部，再弹出一个保存的`ebp`。至于`ret`，它做的事情更简单：直接从当前栈顶取出一个地址，然后跳过去。也就是说，`ret`自己并不知道“应该回到main”，它只是盲目相信栈顶保存的是正确的返回地址。

![ref2](/assets/images/2026-10-25-MDTask2-for-beginner/ref2.webp)

所以返回地址一旦被改写，函数结束时就不会回到原来的位置，而是会跳到别的地方。栈溢出之所以能从“程序崩溃”进一步发展成“控制程序执行流”，关键就在这里。

64位Linux的参数传递方式又不一样。在System V AMD64调用约定中，前六个整数或者指针参数通常依次放进`rdi`、`rsi`、`rdx`、`rcx`、`r8`、`r9`这几个寄存器，参数更多时才继续放到栈上。不过不管参数用什么方式传递，`call`和`ret`仍然依赖栈来保存返回地址，函数序言和尾声的整体思路也没有变，只是寄存器名字从`esp`、`ebp`变成了`rsp`、`rbp`，每个栈单元通常也从4字节变成8字节。

需要提前说明的是，编译器不一定完全照着上面写的顺序生成代码，局部变量之间可能有对齐空隙，也可能直接把变量放进寄存器。同一个函数用`-O0`和`-O2`编译，栈帧都可能完全不同。因此上面的内容只是一个便于理解的模型，真正分析程序时还是要以反汇编和调试结果为准。

# 栈溢出基本知识

## 栈是怎么溢出的（AI Generated）

```
注：本小节原理内容依然由AI生成。
```

先澄清一个容易混淆的说法：这里讲的栈溢出，不是说递归函数一层层调用导致栈空间被用完，而是说程序往栈上的固定大小缓冲区里写入了超出其长度的数据。例如下面这段代码：

```c
#include <unistd.h>

void vuln(void) {
    char buf[16];
    read(0, buf, 64);
}
```

`buf`只申请了16字节，但`read`却允许从标准输入最多读入64字节。只要输入超过16字节，多出来的内容就不会被自动丢掉，而是继续写到`buf`后面的内存里。`read`本身没有做错，它只是忠实地执行了程序给出的长度；真正的问题在于程序员把长度设置得超过了缓冲区大小。

前面说过，局部变量位于较低地址，往高地址走会依次遇到保护栈帧的填充、保存的`rbp`和返回地址。忽略编译器和保护措施的影响，大致的排列关系如下：

```text
低地址                                                      高地址
┌──────────────┬─────────┬────────────┬──────────────┬────────────┐
│ buf[0..15]   │ padding │ 保存的rbp  │  返回地址    │ 调用者数据 │
└──────────────┴─────────┴────────────┴──────────────┴────────────┘
                 输入数据增长的方向 ────────────────────────────>
```

输入不长时，程序看起来一切正常；输入一旦越过缓冲区边界，就会开始覆盖后面的内容。图中的`padding`表示编译器为了对齐而可能留出的空隙，它并不一定存在，长度也不一定固定。实际做题时不能直接拿`char buf[16]`里的16当作偏移，必须去具体程序里确认保存的`rbp`和返回地址究竟在哪里。

![ref3](/assets/images/2026-10-25-MDTask2-for-beginner/ref3.webp)

返回地址被覆盖以后，函数结束执行`ret`时就会把这个被改过的值取出来当成地址使用。如果它恰好是一个不可执行的地址，程序通常会直接报错退出；如果这个地址被精心构造成程序中某段合法代码的地址，程序的执行流就可能转到那里。

程序把输入写进栈上的缓冲区，输入过长会覆盖后面的数据，返回地址正好是其中最关键的一项，而`ret`会不加怀疑地使用它。后面的分析工作，就是确认程序如何接收输入、哪里可能写越界，以及从输入开头到返回地址之间到底隔了多少字节。

# Ret2text

AI讲的原理基本都对，不过说的再多也不如自己上手尝试学得快：ret2text正是基本的栈溢出的最好示例，掌握了ret2text的原理，就基本栈溢出入门了。ret2text即返回（ret）到（2，也就是to）代码节（text在这里是指.text节而不是文本）。下面就以task2来讲解怎么进行ret2text。

## 基础gdb调试与偏移值测量

在这一题中，可以直接看出偏移值，偏移值主要的取决于`你能写入的位置`和`你要控制的返回地址`的距离，从IDA不难看出，buf距离0有0x28（对的，注意这里IDA显示的是十六进制，以及不要直接看buf是32就认为偏移是32，可以看到栈中还有很多padding byte填充字节，这些不属于buf的区域，但是它们会影响偏移值的计算），而ebp还占了4个字节（`__saved_registers`部分），因此我们需要覆盖0x28+0x4一共0x2c的数据才能写入到返回地址，也就是填充的偏移值是0x2c。

当然IDA的栈分析是静态分析，如果遇到复杂的情况（比如要在同一个栈上构造两次溢出，这时候第一次溢出已经破坏完原始栈结构了，再看IDA已经没有什么意义），只看IDA会出错，这里介绍绝对稳妥的调试方法。

当前停在了`call read@plt`，再`ni`一步就会调用read了，不过注意这里read调用前，gdb会分析出函数的参数，这也是后续深入调试一些程序时需要注意的点。还有可以看到下面的调用链并没有显示上一张图的put函数，这是因为显示的是当前函数的调用链，而不是调用历史，我们直接步过了put函数，所以backtrace就没有追踪，等下vuln函数执行完了，vuln也会从backtrace中消失。backtrace在进行ROP分析时是很好用的，可以知道程序走的调用链。好了，继续步过吧：

然后就会发现没动静，这其实是read函数在等待输入，gdb将接下来接收的标准输入给read，我们现在就可以输入内容了，随便输入一点`PWNDBGISAWESOME`:

![ref13](/assets/images/2026-10-25-MDTask2-for-beginner/ref13.webp)

输入完按回车就会到下一条指令`add esp, 0x10`，现在STACK窗口有变化了，出现了我们输入的`PWNDBGISAWESOME`，我们可以用`stack`命令展示更详细的信息：

![ref14](/assets/images/2026-10-25-MDTask2-for-beginner/ref14.webp)

除了我们输入的内容外，注意还有ebp和返回地址，ebp的值不用管，重点看返回地址的值：可以看到栈的`0xffffcb5c`处，记录了返回地址0x80491e9，并且gdb还帮我们把返回地址的内容解析出来了，正是之前提到的`call vuln`的下一条指令`mov eax, 0`。

再看我们写入的内容，记录在栈的`0xffffcb30`处，注意不是`0xffffcb24`哦，`0xffffcb24`实际上记录的是`0xffffcb30`这个地址，只是gdb把`0xffffcb30`地址解析出来了，所以才有个字符串在旁边。那么我们就可以根据字符串写入的位置`0xffffcb30`与返回地址的存储位置`0xffffcb5c`计算偏移，5c-30刚好是2c，和我们之前计算的值一样。

当然可以有更简单的判断偏移方法，我们用`r`命令重跑程序，然后重新运行程序到read的输入处：

![ref15](/assets/images/2026-10-25-MDTask2-for-beginner/ref15.webp)

使用cyclic命令生成1024长度的字符（只要长度大于缓冲区大小，绝对能覆盖到返回地址即可），复制这一串字符，然后read的时候输入：

![ref16](/assets/images/2026-10-25-MDTask2-for-beginner/ref16.webp)

可以发现读入之后，栈已经都是这些乱七八糟的字符了，由于栈被破坏，返回地址被覆盖，backtrace也无法追踪调用链了，接下来只需要继续运行到程序崩溃：

![ref17](/assets/images/2026-10-25-MDTask2-for-beginner/ref17.webp)

程序ret命令返回到了一个无效的地址`0x6161616c`，这里地址是小端序，需要反转一下，对应我们cyclic中生成的laaa，因此我们用cyclic检查laaa在那1024个字符中的哪里，便能得到偏移：

![ref18](/assets/images/2026-10-25-MDTask2-for-beginner/ref18.webp)

cyclic得出偏移是44，也就是0x2c，和前面的计算完全一致。cyclic生成的其实并不是随机字符串，而是每一段都是有规则，不重复的，因此可以借由它快速定位偏移。

## exp编写

程序中给出了一个`MD_PWN_task2`函数，并且给了提示要让这个函数运行起来，函数内还有`system("/bin/sh")`，在上面的演示中，我们已经控制了返回地址，接下来就让程序返回到这个函数就好了。

![ref19](/assets/images/2026-10-25-MDTask2-for-beginner/ref19.webp)

下面是exp编写，这里只展示32位的内容，64位的题目也是差不多的，请自行调试编写exp。

```python
from pwn import *

io = process('./ret2text32')
e = ELF('./ret2text32')
context.log_level = 'debug'

payload = b'A' * 0x2c + p32(e.symbols['MD_PWN_task2'])
io.sendlineafter(b':\n', payload)
io.interactive()
```

简单讲一下就好，用到了python的pwntools库，也就是对应`from pwn import *`；命名了一个io的变量去读取进程，读取进程则用到了`process('./程序文件')`的方式，同理用ELF去读文件的elf结构，前者是动态的获取进程，后者是静态的获取文件结构，如果不理解可以先不管，暂时先记住这个写法就好了；`context.log_level`设为debug，这样运行脚本的时候，可以看到exp与进程之间的具体互动，以此修改我们的exp。

核心部分是`payload = b'A' * 0x2c + p32(e.symbols['MD_PWN_task2'])`，根据计算的偏移值，我们填充了0x2c个大写字母A，然后返回地址部分直接从elf文件中读取符号`MD_PWN_task2`，再用p32打包成32位地址，这样就能确保覆盖返回地址为`MD_PWN_task2`函数的地址，payload写好以后，使用send、sendline、sendlineafter这样的函数去发送，具体的区别和用法可以自行搜索，最后使用`io.interactive()`开启程序交互，整个过程结束，pwn的exp写法基本都是这样，不理解可以先记着，打多了就懂该具体怎么做了。打通了应该是这样的：
